PENJELASAN ENDPOINT /api/mkbd/all-data-full
============================================

Bayangin lu lagi pesen makanan di restoran prasmanan.
Ada 98 menu yang harus disajikan ke meja lu sekaligus.
Endpoint ini tugasnya: nyiapin semua 98 menu itu, terus nata
di piring yang rapi sebelum dianter ke lu.

Komponennya cuma 4 file. Gw jelasin satu-satu pakai analogi
restoran tadi.


-----------------------------------------------------------
1. SqlScript.java  ->  KARTU MENU
-----------------------------------------------------------

Ini cuma "data pembungkus". Isinya 4 informasi:

  - type   : "detail" atau "summary" (kategori menu)
  - vd     : "vd51", "vd52", dst (sub-kategori)
  - baris  : "baris30", "baris65_69", dst (nomor menu)
  - sql    : isi query SQL-nya (resep masakannya)

Jadi 1 file .sql = 1 SqlScript = 1 kartu menu.
Gak ada logic, cuma tempat nyimpen info.


-----------------------------------------------------------
2. SqlScriptRegistry.java  ->  BUKU MENU RESTORAN
-----------------------------------------------------------

Ini yg jalan PERTAMA KALI pas aplikasi nyala (lihat anotasi
@PostConstruct = "jalanin pas startup").

Tugasnya:
  a. Scan folder src/main/resources/sql/ cari semua file .sql
  b. Baca isinya satu-satu
  c. Buang titik-koma (;) di akhir kalo ada
       -> Oracle JDBC error kalo ada ';' di akhir
  d. Bungkus jadi SqlScript, simpen di list

Hasilnya: list 98 SqlScript, siap dipake kapan aja.

Kenapa dibaca pas startup, bukan pas user request?
  -> Biar request user gak nunggu baca file dari disk.
  -> Baca file lambat, baca dari memori cepet.
  -> Sekali baca, bisa dipake selamanya sampai app restart.


-----------------------------------------------------------
3. SqlScriptExecutor.java  ->  KOKI
-----------------------------------------------------------

Ini yang masak (execute query ke Oracle).

Method utama: runAsync(script, genDate)

Yang dia lakuin:
  a. Ambil SQL dari SqlScript
  b. Ganti :genDate di SQL pake tanggal yang dikirim user
  c. Kirim ke Oracle, tunggu hasilnya
  d. Hasil dari Oracle kolomnya UPPERCASE_SNAKE (NAMA_NASABAH)
     -> Diubah jadi camelCase (namaNasabah) biar JSON rapi
  e. Return list of Map (1 Map = 1 baris hasil query)

Kata "Async" artinya: dia gak nunggu selesai, langsung balikin
"janji" (CompletableFuture). Janjinya: "nanti hasilnya dateng".

Kenapa async? Biar 98 query bisa jalan BARENGAN, bukan satu-
satu. Kalo satu-satu, misal 1 query 1 detik = 98 detik. Kalo
barengan (paralel), bisa selesai cuma ~10 detik.

Tapi ada batas: pool-nya cuma 6 (lihat AsyncConfig). Jadi
sebenernya yg jalan barengan max 6 query. Sisanya antri.
Kenapa cuma 6? Biar koneksi Oracle (max 10) gak abis kepake
endpoint ini doang, masih ada 4 buat endpoint lain.


-----------------------------------------------------------
4. MkbdAllDataFullService.java  ->  MANAGER RESTORAN
-----------------------------------------------------------

Ini yg ngatur semua. Dipanggil dari controller.

Alurnya:

  Step 1: Ambil 98 SqlScript dari Registry
  Step 2: Suruh Executor jalanin SEMUA 98 query (paralel)
          -> Dapet 98 "janji" (futures)
  Step 3: Tunggu sampai SEMUA selesai
          (CompletableFuture.allOf(...).join())
  Step 4: Susun hasilnya jadi struktur nested:

    {
      "genDate": "2026-05-05",
      "detail": {
        "coa": [...],
        "vd51": {
          "baris30": [...],
          "baris31": [...],
          ...
        },
        "vd52": {...},
        ...
      },
      "summary": {
        ...
      }
    }

  Step 5: Return ke controller, controller kirim ke user.

Anotasi @Cacheable artinya:
  -> Hasil disimpen di memori 2 menit (lihat CacheConfig)
  -> Kalo ada user lain minta tanggal yang sama dlm 2 menit,
     gak perlu jalanin 98 query lagi, langsung kasih hasil
     dari memori. Cepet banget.
  -> Lewat 2 menit, cache ilang, query ulang ke DB.

Kenapa cuma 2 menit? Karena data ledger bisa berubah dlm
sehari. Kalo cache kelamaan, user dapet data basi.


-----------------------------------------------------------
RINGKASAN ALUR (POV 1 REQUEST USER)
-----------------------------------------------------------

User hit:  GET /api/mkbd/all-data-full?genDate=2026-05-05

  1. Controller terima request
  2. Service dicek dulu: "ada di cache gak utk tgl ini?"
     - Kalo ADA  -> langsung balikin hasil cache. Selesai.
     - Kalo GAK ADA -> lanjut step 3
  3. Service ambil 98 SqlScript dari Registry (yg udah
     disiapin pas startup)
  4. Service kirim 98 query ke Executor, jalan paralel
     (max 6 barengan)
  5. Tunggu semua selesai
  6. Susun hasil 98 query jadi struktur JSON nested
  7. Simpen di cache (utk 2 menit ke depan)
  8. Balikin ke user


-----------------------------------------------------------
KENAPA DESAINNYA KAYAK GINI? (TANYA-JAWAB)
-----------------------------------------------------------

T: Kenapa SQL ditaro di file .sql, bukan langsung di Java?
J: Biar SQL yang panjang gak bikin Java file berantakan.
   Mau nambah query baru? Drop file .sql doang, gak perlu
   ubah Java sama sekali.

T: Kenapa pake interface projection di endpoint /all-data
   yang lama, tapi pake Map<String,Object> di sini?
J: Karena 98 query bentuk hasilnya beda-beda semua. Kalo
   bikin 98 interface projection, capek + bloated. Map
   lebih fleksibel buat data dinamis.

T: Kenapa convert snake_case ke camelCase?
J: Standar JSON itu camelCase (namaNasabah). Oracle balikin
   UPPER_SNAKE (NAMA_NASABAH). Biar JSON-nya enak dibaca
   frontend, di-convert dulu sebelum return.

T: Kenapa pakai LinkedHashMap, bukan HashMap biasa?
J: LinkedHashMap inget urutan masukin. Jadi key di JSON
   keluar urut ("detail" dulu, baru "summary"). HashMap
   urutannya random.


-----------------------------------------------------------
KESIMPULAN
-----------------------------------------------------------

Inti endpoint ini cuma 3 hal:

  1. BACA 98 file SQL pas app nyala (sekali aja, simpen di
     memori).
  2. JALANIN 98 query PARALEL pas user request (max 6
     barengan biar gak ngabisin koneksi DB).
  3. CACHE hasil 2 menit biar request berulang super cepet.

Sisanya cuma "kerapihan": ngubah nama kolom, nyusun struktur
nested, handle error.

Kalo lu paham 3 hal di atas, lu paham 90% endpoint ini.
